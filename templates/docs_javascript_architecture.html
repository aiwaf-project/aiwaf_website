Node.js Architecture and Middleware Decisions

The Node package has one Express-compatible enforcement pipeline. Framework adapters translate their request and response APIs into that pipeline, while storage and model modules provide the state read by each check.

How AIWAF works: system architecture

Adapter boundary

js/index.js exports the main middleware and Fastify, Hapi, Koa, NestJS, Next.js API-route, AdonisJS, and Sails adapters. Each adapter maps its framework's request and response methods into the core contract and translates an early rejection back into the framework.

Body parsing must happen before protections that inspect parsed fields. Next.js integration uses the Node-style API-handler contract; a Fetch API or Edge request is a different boundary. An adapter is responsible for continuation and response completion, not for maintaining a separate policy implementation.

Middleware construction and request planning

wafMiddleware.js normalizes configuration, loads path rules, initializes check modules, and creates the middleware function. Each request resolves its path, method, client address, and route plan. shouldApply combines global middleware selection with the route plan.

The logger is attached before the ordinary checks when enabled. A shared denial helper records the reason and sends a status with a JSON or text error according to the request and configuration. A rejected request returns early instead of calling the downstream handler.

Actual enforcement sequence

The current core executes the following sequence for a request. Individual layers run only when enabled and applicable:

  1. Attach logging and request timing; resolve the route plan.
  2. Enforce the global method policy when enabled. This happens before the request-exemption shortcut.
  3. Check IP/path exemptions, then the active blacklist.
  4. Validate headers and any enabled WASM header, URL, content, or recent-behavior checks.
  5. Apply geo policy, honeypot timing, and rate/flood limits.
  6. Inspect static and learned malicious keywords, then UUID probing.
  7. Evaluate the eligible unknown-route anomaly path.
  8. Attach completed-response keyword learning and call next() for an allowed request.

Method rejection can return 405; ordinary rate excess can return 429; blacklist and other blocking paths can return 403. The configured checks decide whether a denial also changes IP reputation.

What unknown-route anomaly detection means

The core compares the requested path with discoverable Express-style routes. If the route table is unavailable or empty, it treats the request as known rather than applying aggressive unknown-route anomaly detection to every proxied request.

For an eligible unknown route, the anomaly module scores features. A positive model result alone is insufficient: the model must meet training-volume requirements and recent-behavior analysis must confirm scanning-related activity before the core issues its anomaly block. This gate explains why a suspicious score and an actual denial can differ.

Route analysis becomes a per-request plan

sourceAst.js uses bounded handler-source analysis to infer API, form, and authentication intent. pathManifest.js combines source signals with live framework route extraction. The compiler turns discovered protections into path overrides; it does not take over the framework router.

pathRules.js evaluates those rules with route metadata for each request. Explicit policy can disable one check or override rate limits for a prefix. Rebuilding a manifest is a discovery operation; enforcing its compiled policy is a runtime operation.

Response hooks and offline learning

For allowed requests, a response finish hook supplies the actual status to keyword learning. That hook runs after the handler response finishes; it cannot undo an already delivered response. The middleware logger also observes completion.

  1. Request logsCompleted responses supply paths, client identity, status, and timing.
  2. Feature extractionRecords are normalized and combined with per-client activity windows.
  3. Train and reviewVolume thresholds gate model training; route exemptions filter learned keywords.
  4. Publish artifactsThe runtime loads persisted model state and updated learned keywords.

The training job is separate from ordinary application request handling. Reading logs and rebuilding a forest does not need to happen for every request. Runtime keyword learning, where enabled, is a separate mechanism that can use completed-response signals.

Offline training reads configured access logs or middleware records and persists a language-native forest artifact. Review feature and model compatibility before moving artifacts between Node, Rust/WASM, Python, and Java.

The feature order is part of the model contract. A trainer and scorer must agree on the order, status mapping, time units, and window semantics. Summary fields ending in _ms use milliseconds; the feature vector uses seconds. Sharing feature names alone does not make every model artifact interchangeable.

Optional WASM execution

wasmAdapter.js loads available Rust-backed primitives and converts JavaScript inputs into the WASM representation. The middleware still decides which checks apply, what to log, and when to reject a request. If initialization or conversion is unsuitable, JavaScript implementations remain available.

Crossing the binding boundary has a fixed conversion cost. Large feature batches and forest workloads can benefit; small object-heavy calls may be faster in JavaScript. WASM is a computation backend, not a separate HTTP firewall service.

Worked example: one denied request

A nonexempt request with valid headers reaches the rate limiter. If its shared or local window exceeds the configured maximum, the middleware marks the denial, sends 429 unless a flood or blacklist path determines another status, and returns. The application handler does not run. Logging can still observe the completed denial because its hook was attached earlier.
