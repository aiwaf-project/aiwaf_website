Testing an AIWAF-protected application

{% include '_docs_source.html' %}

Test both the application's successful responses and the protection decisions that can stop a request before its handler. Start with deterministic limits, then add the full middleware stack and deployment checks.

Choose the right test boundary

LayerWhat to verifyWhat it proves
Application testsValidation, authentication, business rules, and successful response bodies.The handler behaves correctly when reached.
Focused protection testsAn allowed request, a rejected request, and a scoped exemption for one enabled check.The middleware is registered and enforces the intended policy.
Full application integrationActual middleware order, route manifest, headers, storage, and known model fixtures.The checks work together with your framework and application.
Deployment testsReal proxy/client identity, repeated requests across workers, shared state, and health probes.The deployed topology behaves as intended.

Keep a successful request beside each rejection assertion. A suite where every request fails can hide a broken registration, missing route, or overly broad policy. The examples below enable only rate limiting so an unrelated header or model check cannot cause an accidental pass.

Isolate state before writing assertions

  • Use a fresh application or test client lifecycle and dedicated data, log, and model locations. CSV files and Redis state do not roll back with a database transaction.
  • Give parallel workers separate cache namespaces, databases, or directories. Keep one namespace shared only for tests explicitly checking cross-worker behavior.
  • Use fixed route budgets and an isolated manifest path. A discovered route policy can override the global limit, so test the effective route policy.
  • Keep the client identity stable while testing a bucket. Use a new identity when testing independent clients.
  • Use a known JSON model fixture for anomaly decisions. Do not train on live traffic as part of a deterministic application test.
  • For window expiry tests, control the clock at the component boundary or use a dedicated timed integration test. Avoid long sleeps in ordinary tests.

Django's test runner creates test databases, but caches are not automatically isolated or cleared between tests. Use a dedicated test cache before clearing it. See Django's testing overview.

Write and run Flask protection tests

Create an empty working directory, install aiwaf[flask], and save this complete file as test_flask_protection.py. It builds a new application and temporary CSV directory for every test, explicitly selects memory counters, and pins both route budgets.

python -m pip install "aiwaf[flask]"

test_flask_protection.py

"""Run with: python -m unittest discover -s examples/testing -p test_flask_protection.py -v"""

from pathlib import Path
import tempfile
import unittest

from flask import Flask
from aiwaf.flask import AIWAF, aiwaf_exempt, aiwaf_exempt_from


class ProtectionTests(unittest.TestCase):
    def setUp(self):
        # A new application and state directory for every test.
        directory = tempfile.TemporaryDirectory(prefix=".ci-protection-validation-", dir=Path.cwd())
        self.addCleanup(directory.cleanup)
        app = Flask(__name__)
        app.config.update(
            TESTING=True,
            AIWAF_USE_CSV=True,
            AIWAF_DATA_DIR=directory.name,
            AIWAF_RATE_CACHE_BACKEND="memory",
            AIWAF_PATH_MANIFEST=str(Path(directory.name) / "paths.json"),
            AIWAF_RATE_WINDOW=60,
            AIWAF_RATE_MAX=3,
            AIWAF_RATE_FLOOD=100,
            AIWAF_PATH_RULES=[
                {"PREFIX": path, "RATE_LIMIT": {"WINDOW": 60, "MAX": 3, "FLOOD": 100}}
                for path in ("/api/message", "/api/preview")
            ],
        )

        @app.get("/api/message")
        def message():
            return {"message": "Protected"}

        @app.get("/health")
        @aiwaf_exempt
        def health():
            return {"ok": True}

        @app.get("/api/preview")
        @aiwaf_exempt_from("rate_limit")
        def preview():
            return {"message": "Preview"}

        AIWAF(app, middlewares=["rate_limit"])
        self.client = app.test_client()

    def test_protected_route_throttles(self):
        for _ in range(3):
            response = self.client.get("/api/message")
            self.assertEqual(response.status_code, 200)
            self.assertEqual(response.json, {"message": "Protected"})
        response = self.client.get("/api/message")
        self.assertEqual(response.status_code, 429)
        self.assertEqual(response.json, {"error": "too_many_requests"})

    def test_health_stays_available_after_throttling(self):
        for _ in range(4):
            self.client.get("/api/message")
        response = self.client.get("/health")
        self.assertEqual(response.status_code, 200)
        self.assertEqual(response.json, {"ok": True})

    def test_selective_exemption_bypasses_rate_limit(self):
        self.assertEqual(
            [self.client.get("/api/preview").status_code for _ in range(5)],
            [200] * 5,
        )


if __name__ == "__main__":
    unittest.main()

python -m unittest discover -s . -p test_flask_protection.py -v

Expect three passing tests. The first verifies three successful responses followed by HTTP 429 and the exact too_many_requests JSON body. The others verify health availability after the protected route is throttled and that a selective rate-limit exemption permits repeated requests.

Checkpoint: Change the expected throttle status from 429 to 200 and rerun: that assertion should fail. Restore it afterward. This confirms the test can detect the behavior it claims to check.

This fixture exercises AIWAF behavior independently. In your own project, also test your actual app factory and live routes so a mistake in production registration cannot be hidden by a separate fixture.

Write and run Django protection tests

In a separate empty directory, install aiwaf[django] and save both files below. The fixture uses Django's test client, ORM-backed AIWAF stores, an in-memory SQLite test database, and a dedicated local-memory cache. The URL configuration is the test module itself.

python -m pip install "aiwaf[django]"

django_test_settings.py

"""Settings for this standalone example, separate from your application's settings."""

from pathlib import Path

SECRET_KEY = "local-documentation-test-key"
INSTALLED_APPS = ["aiwaf.django"]
DATABASES = {"default": {"ENGINE": "django.db.backends.sqlite3", "NAME": ":memory:"}}
DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"
# Only for this standalone fixture: create AIWAF tables without generated migrations.
MIGRATION_MODULES = {"aiwaf": None}
ROOT_URLCONF = "test_django_protection"
ALLOWED_HOSTS = ["testserver"]
MIDDLEWARE = ["aiwaf.django.middleware.RateLimitMiddleware"]
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.locmem.LocMemCache",
        "LOCATION": "documentation-protection-tests",
    }
}
AIWAF_USE_CSV = False
AIWAF_PATH_MANIFEST = str(Path(__file__).with_name("unused-test-manifest.json"))
AIWAF_RATE_WINDOW = 60
AIWAF_RATE_MAX = 3
AIWAF_RATE_FLOOD = 100
AIWAF_EXEMPT_PATHS = ["/health"]
AIWAF_SETTINGS = {
    "PATH_RULES": [
        {"PREFIX": "/api/message", "RATE_LIMIT": {"WINDOW": 60, "MAX": 3, "FLOOD": 100}},
        {"PREFIX": "/api/preview", "DISABLE": ["rate_limit"]},
    ]
}

test_django_protection.py

"""Run from this directory using django_test_settings; see /docs/testing."""

from django.core.cache import cache
from django.http import JsonResponse
from django.test import TestCase
from django.urls import path


def message(request):
    return JsonResponse({"message": "Protected"})


def health(request):
    return JsonResponse({"ok": True})


def preview(request):
    return JsonResponse({"message": "Preview"})


urlpatterns = [
    path("api/message", message),
    path("health", health),
    path("api/preview", preview),
]


class ProtectionTests(TestCase):
    def setUp(self):
        # django_test_settings points only at a dedicated local-memory test cache.
        cache.clear()
        self.addCleanup(cache.clear)

    def test_protected_route_throttles(self):
        for _ in range(3):
            response = self.client.get("/api/message")
            self.assertEqual(response.status_code, 200)
            self.assertEqual(response.json(), {"message": "Protected"})
        response = self.client.get("/api/message")
        self.assertEqual(response.status_code, 429)
        self.assertEqual(response.json(), {"error": "too_many_requests"})

    def test_health_stays_available_after_throttling(self):
        for _ in range(4):
            self.client.get("/api/message")
        response = self.client.get("/health")
        self.assertEqual(response.status_code, 200)
        self.assertEqual(response.json(), {"ok": True})

    def test_selective_exemption_bypasses_rate_limit(self):
        self.assertEqual(
            [self.client.get("/api/preview").status_code for _ in range(5)],
            [200] * 5,
        )

python -m django test test_django_protection --settings=django_test_settings -v 2

Expect three passing tests and creation/destruction of the test database. TestCase isolates ORM changes; setUp() and cleanup clear only the dedicated local-memory cache. The standalone fixture disables AIWAF migrations to create its tables directly. In an existing project, keep your real migrations, include AIWAF in INSTALLED_APPS, and run your application's tests with its dedicated test settings.

Adapt these assertions to the routes from the Django setup guide. Keep another suite using your real ROOT_URLCONF and complete MIDDLEWARE list: this focused fixture intentionally exercises only the rate limiter.

Django route-policy detail

This fixture uses AIWAF_EXEMPT_PATHS for health and a PATH_RULES entry disabling only rate_limit for preview. In the current source, the rate limiter runs before Django resolves the view, while decorator detection reads request.resolver_match. A selective decorator alone did not bypass the limiter in this full test-client request. Use the explicit path policy for this case, and test decorators through your actual middleware stack.

Apply the same assertions to other frameworks

The status sequence and test structure above belong to these Python fixtures. For other runtimes, use that runtime's configuration names, response contract, and policy precedence.

  • FastAPI: use its test client against the actual ASGI application. Keep the client in a context manager when startup/shutdown initializes resources. Give each test its own policy/state configuration; see the FastAPI setup guide.
  • Node.js: create a fresh app and AIWAF middleware instance per test. Use the framework's injection facility or an HTTP client against an ephemeral local port. Verify a normal response, configured throttle/block response, and exemption. See Node.js operations.
  • Java: test the engine decision independently, then exercise the registered Spring filter or Servlet filter through your framework test harness. Keep shared Redis integration tests separate from memory-backed tests. See Java operations.

Expand to the full protection stack

  • Headers and parsing: pair valid browser/API requests with requests violating your configured requirements. Assert the rejection reason or body as well as status.
  • Exemptions: verify that the intended check is bypassed and that another enabled check still runs. The rate-only examples prove the bypass, but do not prove other checks remain active.
  • Flood and reputation: distinguish a soft throttle from a hard block. Verify persistent state and later requests separately using disposable storage.
  • Models: cover a known normal sample, a known anomaly, and missing/invalid model handling for your configured runtime. Keep training tests separate from inference tests.
  • Route discovery: generate the manifest from the test application's live route table, verify the protected route is present, and repeat the behavior assertions with the manifest loaded.
  • Observation: check the expected log record and response status, including denied requests, without relying on a production log file.

For Redis or multiple workers, send a combined request sequence across workers using the same client identity and bucket. Assert the aggregate budget, expiry behavior, and configured backend-failure behavior. A single-process in-memory test cannot establish those guarantees.

Run the examples in continuous integration

From the AIWAF website checkout, the checked-in examples run with these commands. Install the relevant framework extras first.

python -m unittest discover -s examples/testing -p test_flask_protection.py -v
cd examples/testing
python -m django test test_django_protection --settings=django_test_settings -v 2

Run application and focused protection tests on each change. Run shared-backend and deployed-topology checks in a separate integration job with disposable services. Save failure output and effective policy configuration so failures can be reproduced locally.

Diagnose a failing protection test

FailureCheck next
Expected 429, got 200Middleware registration, route/IP exemptions, effective manifest rules, changing client identity, and counters split across workers.
First request already rejectedLeaked cache/blocklist state, missing required headers, route mismatch, or another enabled check.
Passes alone, fails in the suiteShared storage/cache keys, module-level app reuse, test order, and model/manifest files left by another test.
Expected JSON, got HTML or a redirectWrong URL, trailing-slash routing, framework exception handling, or a response produced by the application/proxy.
