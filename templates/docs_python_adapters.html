How AIWAF works: system architecture

Django

Add aiwaf.django to INSTALLED_APPS. Use aiwaf.django.middleware.all for the unified stack or explicitly order individual middleware classes. Django supports ORM-backed or CSV runtime stores and file, database, or cache model storage. Apply migrations when using ORM stores.

Flask

from aiwaf.flask import AIWAF exposes the application integration. Request and response hooks coordinate checks, decorators, logging, and model scoring. Initialize AIWAF once; select middlewares=["auto"], ["all"], or a list of canonical middleware names.

FastAPI

from aiwaf.fast import AIWAF exposes the Starlette-based orchestrator. Pass structured constructor options for storage, header validation, rate limiting, and logging. FastAPI uses the shared runtime storage and route-policy helpers. Version 1.0.8 normalizes headers before Rust validation and respects the adapter's disabled Rust path.

Route helpers

Django, Flask, and FastAPI expose equivalent route helpers:

from aiwaf.flask import (
    aiwaf_exempt,
    aiwaf_exempt_from,
    aiwaf_only,
    aiwaf_require_protection,
)

@app.get("/health")
@aiwaf_exempt
def health():
    return {"ok": True}

@app.post("/webhook")
@aiwaf_only("header_validation")
def webhook():
    return {"accepted": True}

Canonical middleware names include header_validation, rate_limit, ip_keyword_block, honeypot, geo_block, uuid_tamper, ai_anomaly, and logging.

Middleware selection

auto starts from the canonical middleware set and omits checks that are not useful for detected application signals. Route manifests complement live metadata. Generate the manifest from the actual application environment after its routes have been registered.
