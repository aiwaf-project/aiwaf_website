How AIWAF Works

AIWAF sits inside the application request lifecycle. Framework adapters turn live HTTP requests into policy inputs, deterministic controls make immediate decisions, and optional anomaly models add evidence from recent behavior.

Two connected execution paths

The system has a request path for enforcing the current policy and a learning path for improving future decisions. Configuration, route metadata, runtime stores, and model artifacts connect them.

  1. Framework adapterExtract method, path, headers, client address, and available handler metadata.
  2. Policy and checksSelect applicable protections, read state, and return an early denial when a check fails.
  3. Application handlerAllowed requests reach the normal application code.
  4. Response observationsRecord status, duration, and behavior; response-aware adapters may make another decision.

This is a conceptual flow, not a universal middleware ordering. Python wrappers, Node middleware, and Java filters attach to different framework hooks. The runtime-specific pages below explain the actual execution boundaries.

How route policies become decisions

A manifest records discovered routes, methods, and inferred handler intent. Source analysis can supply signals such as JSON responses, form handling, or authentication calls when framework metadata is incomplete. The manifest compiler translates those signals into middleware disablement and rate-limit overrides.

The runtime combines those generated rules with explicitly configured path policies and decorator or annotation metadata. A protection runs only when it is enabled and applicable under that runtime's policy rules. An auto selection starts from the canonical set and omits checks unsupported by detected application signals; it is not itself an anomaly detector.

For example, an API endpoint may omit HTML form timing while keeping headers and rate limits. A login form needs different checks. Keep inferred policies reviewable: a route name or return type is evidence about intent, not proof of authorization.

A block is a decision; a blocklist is state

A failing header, method, or rate check can reject the current request. Some checks also record an offense or create a temporary IP block. Those are separate effects: returning a denial does not imply that every later request is permanently blocked.

Reputation handling records weighted offenses and can escalate temporary block durations. Later requests consult block expiry and exemption rules. Which checks mutate reputation and which response statuses they return are runtime-specific.

State ownership explains multi-worker behavior

State categoryTypical contentsArchitectural consequence
Recent enforcement stateRate buckets, form timestamps, UUID scores, recent request history.Independent worker memory creates independent windows and counts.
Operational storesBlacklists, exemptions, geo policy, learned keywords.Persistence across restarts is different from consistent access across processes.
Model artifactsForest state, feature schema, training metadata.Loading the same artifact does not share rate-limit or blacklist state.

A local file can persist data while leaving other request counters process-local. Choose sharing separately for every state category. Java's Redis backend shares enforcement state atomically; Node rate limiting accepts a shared cache; Python sharing depends on the adapter and its configured stores.

How anomaly detection contributes

An Isolation Forest repeatedly partitions feature samples using random feature choices and split points. Samples isolated in fewer splits tend to receive more anomalous scores. The forest learns a distribution of request behavior; it does not identify a vulnerability or understand the application's authorization rules.

The host runtime decides whether a score is enough to block. Model availability, training volume, thresholds, route eligibility, and recent-behavior confirmation can all affect that decision. For example, Node's unknown-route path requires both a sufficiently trained model and scanning-related behavior before issuing an anomaly block.

The feature order is part of the model contract. A trainer and scorer must agree on the order, status mapping, time units, and window semantics. Summary fields ending in _ms use milliseconds; the feature vector uses seconds. Sharing feature names alone does not make every model artifact interchangeable.

The learning loop

  1. Request logsCompleted responses supply paths, client identity, status, and timing.
  2. Feature extractionRecords are normalized and combined with per-client activity windows.
  3. Train and reviewVolume thresholds gate model training; route exemptions filter learned keywords.
  4. Publish artifactsThe runtime loads persisted model state and updated learned keywords.

The training job is separate from ordinary application request handling. Reading logs and rebuilding a forest does not need to happen for every request. Runtime keyword learning, where enabled, is a separate mechanism that can use completed-response signals.

Current Python model persistence uses JSON rather than executable Python-object serialization. Java can exchange the Python Rust-model forest state for the supported schema. JavaScript-native artifacts and legacy formats require their own compatibility checks.

What happens after the handler

Response observations make real status and duration available. This matters for distinguishing a normal request from repeated 404 probing. A response-aware integration may evaluate behavior after the handler returns, but a response already committed or streamed to the client cannot be replaced.

Java's Spring filter explicitly distinguishes an uncommitted synchronous response from committed or asynchronous output. Other adapters use their framework's hooks for logging and learning. Avoid assuming that post-response scoring can prevent every byte from leaving the application.
